# 경제흐름 V2 설계 — 초보자 질문과 과거 기사 기억

- 작성일: 2026-09-11
- 상태: V2.1 구현, 기사별 사용자 피드백을 반영해 재평가 중. V26은 격리된 평가 DB에서 검증했으며 V2.1과 함께 DEV 배포 대상이다. PROD 반영·기존 공개 브리핑 갱신은 별도다.
- 현재 운영 기준: [운영 가이드](ECONOMIC_FLOW_OPERATIONS.md), [V1 상세 설계](ECONOMIC_FLOW_DAILY_BRIEFING_FINAL_DESIGN_V1.md), [V1 프롬프트 계약](ECONOMIC_FLOW_LLM_PROMPT_DESIGN_V1.md)
- 첫 평가 양식: [사용자 비교 평가](ECONOMIC_FLOW_BEGINNER_MEMORY_REVIEW.md)

## 1. 목표와 결정

독자가 오늘의 경제 변화를 읽다가 이해하지 못하는 연결고리를 질문으로 찾아, 일반 경제원리와 해당 사건의 기사 근거로 설명한다. 과거 기사에 나온 결정·이유·조건을 다시 찾을 수 있도록 보관한다. 질문과 기억의 품질 기준은 사용자의 실제 피드백으로 구체화한다.

제품 결과는 흐름별 제목, 쉬운 요약 본문, 본문 아래 펼쳐진 질문·답변, 근거 기사·원문이다. 본문과 답변은 자연스러운 ~요체로 쓴다. `watchPoints`와 ‘앞으로 확인할 것’은 V2 생성 계약과 화면에서 제거한다. 기존 결과 JSON은 지우지 않고 새 화면에서 해당 항목을 표시하지 않는다.

질문은 이해에 필요한 핵심 개념의 ‘무엇인가요?’에서 시작해 ‘왜 그런 결과로 이어지나요?’까지 다룬다. 용어의 한글 풀이만 쓰거나 뒷답변에서 뜻을 유추하게 하지 않는다. 정의를 추가한다고 유용한 연결 질문을 삭제하지 않는다. 모든 명사를 사전처럼 나열하지 않고 기사·후속 설명을 이해하는 데 필요한 개념을 선정한다.

핵심 결정:

1. 기존 네 테이블과 PostgreSQL/pgvector를 재사용한다. 노드 그래프와 관계 판정 체인을 만들지 않는다.
2. 기사 보관, 오늘의 브리핑 채택, 장기 검색 대상으로 채택하는 결정을 분리한다.
3. 원문에 직접 있는 사실·이유만 사건 기억으로 저장한다. 최종 설명, Q&A, LLM의 일반 지식은 기사 기억에 넣지 않는다.
4. 기존 관측 추출 호출에서 기억 후보 선정도 수행한다. 기존 Terra 설계 호출에서 초보자 질문도 선정한다.
5. 코드가 질문에 맞는 근거를 검색하고, 기존 Luna 편집 호출에서 본문과 Q&A를 함께 작성한다.
6. 질문 선정과 기억 선정을 별도 평가한다. 사용자의 자연어 피드백을 기준 사례와 회귀시험으로 남긴다.

‘LLM이 경제 초보자가 될 때까지’는 필요한 질문을 놓치지 않고, 불필요한 설명과 사소한 기억을 줄여 사용자 기준에 반복적으로 맞추는 목표로 다룬다. 피드백만으로 모델 가중치가 자동 학습되는 것은 아니다. 이 단계에서는 선정 규칙·프롬프트·짧은 예시·검색 조건을 수정하고 버전을 관리한다. 파인튜닝은 현재 범위에 없다.

## 2. 현재 설계에서 달라져야 하는 부분

| 현재 동작 | 목표에 대한 한계 | V2 변경 |
|---|---|---|
| 오늘 선택한 기사만 관측 추출 | 오늘 흐름에는 작아도 향후 배경이 될 기사가 빠질 수 있음 | 같은 기사 선별 호출에 기억용 기사 후보도 포함 |
| 추출한 관측을 모두 과거 검색에 사용 | 일일 수치·반복 사실과 장기적으로 유용한 설명이 섞임 | 관측별 장기 검색 허용 여부를 명시 |
| 현재 관측 전체와 비슷한 과거를 검색 | ‘왜 이 결정을 했는가’라는 질문의 답과 다른 후보가 나올 수 있음 | 흐름 설계 후 질문별 검색 추가 |
| 과거를 주로 이전 수치·방향 비교에 사용 | 같은 사업의 목적·제약·정책 배경 활용이 제한됨 | 직접 관련된 과거 배경도 사용하되 시점·대상 일치 확인 |
| 편집기는 확정한 관측만 받아 본문 작성 | 근거가 충분한 질문과 부족한 질문을 구분하지 않음 | 질문별 후보 근거를 받아 Q&A 작성·사용 근거 반환 |
| 평가가 흐름·coverage·숫자 중심 | 사용자가 궁금한 질문과 모델 질문의 차이가 드러나지 않음 | 질문 누락·불필요한 질문·기억 누락·불필요한 기억을 각각 기록 |

V1의 ‘추가 검색용 LLM 없음’은 유지한다. 검색 요청은 기존 설계 모델의 결과에 포함한다. V1의 편집기는 근거를 재선택하지 않았지만, V2 편집기는 **추가 검색으로 받은 Q&A 후보 중 직접 답을 지지하는 근거를 고르는 책임**을 맡는다. 흐름의 묶음·순서·현재 기사 coverage는 변경하지 않는다. 이 책임 확대의 정확성은 별도로 평가하며, 검증 없이 모델 능력을 가정하지 않는다.

## 3. 전체 처리 과정

```text
RSS 기사 목록 보관 — 코드, LLM 호출 없음
  ↓
기존 제목 사전선별 → 제목·요약 정밀선별 — Luna
  ├─ 오늘의 흐름에 필요한 기사
  └─ 기억 후보를 확인할 기사
  ↓ 합집합 중복 제거, 공통 원문·비용 상한 적용
선택 기사 원문 확보
  ↓
원문 관측 + 기억 여부 선정 — 기존 Luna 추출 호출
  ↓ 코드: 원문 문단·숫자·출처 검증
오늘 관측 / 장기 검색 대상 저장 및 필요한 임베딩
  ↓
기존 현재 연결·과거·원리 후보 검색 — 코드
  ↓
흐름 설계 + 초보자 질문 + 부족한 근거 검색 요청 — 기존 Terra 호출
  (직접 근거와 해시가 같은 인접 문단을 중복 제거, 인접 문단은 질문 발견용 3,000자 이내)
  ↓
질문별 과거 기억·기사 목록·경제원리 검색 — 코드
  └─ 관측에 답이 없을 수 있어 상위 관련 기사 원문 확인
      관련 원문 문단을 코드로 제한해 복사, 추가 추출 LLM 호출 없음
  ↓
요약 본문 + 질문·답변 + 답변별 사용 근거 — 기존 Luna 편집 호출
  ↓
코드 검증 → 평가 결과 또는 새 SUCCESS revision
```

현재 브리핑용 기사가 없더라도 기억 후보만 있는 날은 기억 처리를 수행할 수 있다. 기억용 기사만으로 오늘 흐름을 강제로 만들지 않는다. 정상 일일 호출에 별도 질문 생성기·기억 심사기·검증 LLM을 추가하지 않는다. 조회한 과거 원문은 코드로 관련 문단을 복사해 기존 편집기에 전달한다. 별도 추출 호출과 자동 기억 승격은 하지 않는다.

## 4. 무엇을 저장하는가

### 4.1 기사 보관과 엄선된 기억

| 위치 | 보관 내용 | 검색·사용 규칙 |
|---|---|---|
| `articles` | 수집한 제목·RSS 요약·URL·발행시각, 확보한 원문 | 기사 목록은 전체 보관. 본문은 선택·조회된 기사만 확보 |
| `article_observations` | 원문으로 검증한 사실·이유와 출처 문단 | 오늘의 관측은 재현을 위해 보관. 장기 검색에는 선정된 관측만 사용 |
| `economic_principle_chunk` | 기존 경제원리 | 작동 원리 설명에 사용. 특정 사건의 동기·발생 사실을 증명하지 않음 |
| `daily_briefings` | 결과·질문·검색·선정 이력·usage | 평가·운영 진단용. 생성된 본문과 답변은 다음 날 근거로 검색하지 않음 |

기사 목록에 사소한 기사가 있는 것과 엄선된 과거 기억에 사소한 정보가 있는 것은 다르게 관리한다. 전자는 놓친 기사를 다시 찾기 위한 보관이다. 후자는 실제로 검색 품질을 떨어뜨릴 수 있으므로 사용자 평가로 줄인다. 기사 목록에서 후보를 찾았다는 사실만으로 그 기사 내용을 답변 근거로 확정하지 않는다.

### 4.2 기억 선정의 초기 기준

다음은 시험을 시작하기 위한 가설이며, 사용자 정답으로 간주하지 않는다.

- 구체적 정책·사업·투자·공급·자금조달 결정과 원문이 명시한 이유·조건·제약
- 그 결정의 시행, 확대, 지연, 철회 등 나중의 변화와 비교할 수 있는 내용
- 중요한 경제지표의 변화와 원문이 설명한 원인·범위. 단순 숫자라도 이후 비교에 필요하면 남길 수 있음
- 국가·기업·가계의 대응을 설명하는 구체적 계약·정책 조건·이해관계
- 주요 주체가 원문에서 밝힌 입장·전망·예고·약속·행동 조건 중, 후속 발언이나 결정과 비교할 가치가 있는 내용. 일반적인 설명이라도 ‘누가 언제 그 입장을 밝혔다’는 발언 사실은 별도로 기억 가치가 있을 수 있다. 발언자를 유명인 목록으로 제한하거나 재등장 가능성만으로 모든 발언을 저장하지 않는다. 이 확장 기준은 사용자 제안에 따른 평가 가설이며 M01~M03의 개별 승인으로 취급하지 않는다.

일반적으로 제외할 후보는 다음과 같다.

- 같은 기사 안의 반복, 새 정보 없는 재보도, 제목만 바꾼 같은 발표
- 경제적 조건이나 행동을 설명하지 않는 수식어·홍보성 평가·행사 소개
- 이후 설명에 필요한 의미 없이 나열한 부수적 사양·순위·숫자
- 기사에 없는 의도·인과 추론, 일반 상식, AI가 쓴 해설

‘대기업이면 저장’, ‘숫자가 크면 저장’, ‘미래에 쓸 수도 있으면 저장’으로 판단하지 않는다. 동시에 ‘작은 숫자는 버린다’, ‘수치는 모두 사소하다’로 판단하지 않는다. 사용자가 남기고 싶었던 정보가 무엇을 설명하는지 확인해 규칙을 조정한다.

드라기 기사 사용자 피드백으로 구체화한 필수 기준: 정책·투자·행동 제안을 기억할 때는 **그 제안과 제안이 해결하려는 구체적인 문제를 함께 보존한다.** 원문 말미의 ‘하지 않으면 어떤 손실·비용·선택 제약이 생기는가’라는 조건부 우려도 제안의 근거가 된다. ‘성장·주권 확보’라는 목적 표현만으로 그 이유가 충분히 저장됐다고 보지 않는다. ‘왜 그 행동이 필요한가’와 ‘왜 실행이 늦어지는가’는 구분한다.

대상·주체·제안·핵심 이유를 같은 관측 `text`에 연결하고 이유 문단도 `source_snapshot.spans`에 남긴다. 선정 평가용 `memoryReason`에만 이유를 쓰는 것은 검색 가능한 사건 기억을 보완하지 못한다. 기존 0~3개·220자 안에서 핵심 이유를 먼저 보존하고 나머지 관측을 비교 지표·별도 제약에 쓴다. 원문이 밝히지 않은 이유는 추가하지 않으며, 발언자의 우려·주장을 실제 결과나 모든 후속 결정의 원인으로 바꾸지 않는다.

발언 기억을 사용할 때는 발언자·시점·대상·조건과 주장/전망의 성격을 보존한다. 과거 발언은 당시 입장과 이후 변화·일관성을 설명하는 근거가 될 수 있지만, 그 발언 내용이 객관적으로 참이라는 증거나 현재 결정의 직접 원인이라고 자동 처리하지 않는다. 같은 주제의 새 입장·조건·약속인지와 새 정보 없는 반복인지도 구분해 평가한다.

### 4.3 두 번의 선정과 누락 복구

기사 단위로 원문을 읽을 후보를 고르고, 그 원문 안에서 기억할 관측을 고른다. 두 결정은 기존 선별·추출 호출에 포함한다.

- 제목·요약 정밀선별은 `briefingArticles`와 `memoryArticles`를 반환한다. 이유는 한 문장으로 남긴다.
- 원문은 두 목록의 합집합에서 한 번만 처리한다. 오늘의 기사 coverage 검사는 `briefingArticles`에만 적용한다.
- 기존 일일 선택 상한 20개를 우선 유지한다. 오늘의 필수 기사를 먼저 보존하고 남는 범위에서 기억 전용 후보를 확인한다. 모델이 반환한 원출력과 실제 채택 목록을 trace에 남긴다. 모델이 반환하지 않은 탈락 이유는 알 수 없으므로 사후 표본 평가에서 확인한다.
- 제목 사전선별에도 구체적 결정의 목적·제약을 보여주는 기사를 고려하도록 기준을 추가한다. 별도 전체 뉴스 LLM 호출을 만들지 않는다.
- 기사 목록은 남으므로, 당시 선택하지 않은 기사도 이후 질문의 검색 후보가 될 수 있다. 이것은 누락 회수 경로이며 완전한 보관을 보장하지는 않는다.

처음에는 기사당 0~3개·관측당 220자라는 기존 추출 상한으로 시험한다. 목적·조건을 빼야만 상한을 맞출 수 있는 사례는 ‘선정 오류’와 ‘길이·개수 상한에 의한 누락’을 구분한다. 사용자가 필요한 정보를 지목했는데 상한이 원인이라면 해당 상한만 비용과 함께 재평가한다. 세 개를 채우기 위해 사소한 사실을 추가하지 않는다.

### 4.4 관측 계약과 최소 DB 변경

기존 추출 결과의 각 관측에 `remember`와 평가용 한 문장 `memoryReason`을 추가했다.

```json
{
  "observations": [
    {
      "text": "주체·대상 결정·원문에 명시된 이유나 조건이 함께 있는 문장",
      "spanIds": ["P003", "P004"],
      "remember": true,
      "memoryReason": "이 결정의 배경을 이후 설명할 때 필요하다"
    }
  ]
}
```

이 예시는 구조 설명이며 실제 사건의 근거가 아니다. `remember`는 사실·주장 유형이나 중요도 점수가 아니라 장기 검색 허용 여부다. `statementKind`, `role`, `confidence`, `importance` 등은 도입하지 않는다.

같은 추출 호출에서 각 기억 판단의 짧은 이유도 받아 trace와 평가 비교표에 남긴다. 별도 심사 호출은 하지 않으며, 이 이유를 사실 근거나 임베딩 대상에 포함하지 않는다. 모델이 원래 이유를 반환하지 않은 탈락 항목에는 ‘이유 미기록’이라고 표시하고 Codex가 모델의 생각을 추정해 채우지 않는다.

예정된 DB 변경은 `article_observations`에 다음 두 필드를 추가하는 것이다. 실제 migration은 구현 단계에 새 번호로 만든다.

| 추가 필드 | 목적 |
|---|---|
| `memory_eligible` boolean, 기본 false | 장기 기억 검색에 포함할지 결정 |
| `source_snapshot` JSONB | 추출 당시 제목·URL·발행시각·본문 해시·사용한 원문 문단의 정확한 텍스트 보존 |

`source_snapshot`은 코드가 원문에서 복사한다. LLM에게 출처 문단을 다시 쓰게 하지 않는다. 기억 문장과 원문 근거의 ID·숫자 검증은 유지한다. 외부 기사 수정으로 문단 번호가 달라져도 이미 저장한 기억의 근거가 다른 문단으로 바뀌지 않아야 한다.

오늘의 관측은 현재 연결 계산에 필요하면 `remember=false`여도 임베딩한다. 기억 전용 기사에서는 `remember=true`인 관측만 임베딩한다. 같은 관측 벡터는 재사용하며, 부적격 관측을 단지 벡터가 있다는 이유로 과거 검색에 포함하지 않는다.

기존 관측을 모두 자동 승인하지 않는다. 전환 실험에서는 복사한 자료에 새 기준을 적용하고, 검증된 범위부터 장기 검색에 합류시킨다. 기존 서비스 전환 전까지 V1 조회와 자료는 그대로 유지한다.

### 4.5 수정·재사용·중복

- 재사용 키는 기사 ID만으로 충분하지 않다. 원문 해시·추출 모델·프롬프트 버전이 일치해야 한다. 기억 기준을 바꾸면 추출 프롬프트 버전도 바뀐다.
- 현재 `ObservationStore.replace`는 기사별 기존 관측을 삭제하므로 평가 재실행에 운영 DB를 사용하지 않는다. 고정 입력과 이전 출력은 평가 파일에 보존한다.
- 같은 원기사의 개정은 새로 확인한 본문과 근거로 원자적으로 교체한다. 과거 공개 결과의 원문 스냅샷은 그대로 남긴다.
- RSS 제목·요약·URL·발행시각의 개정이 감지되면 기존 본문을 그대로 최신판으로 간주하지 않는다. 해당 기사를 사용할 때 원문을 다시 확인하고, 확보가 실패하면 과거 스냅샷을 이전 시점의 근거로만 표시한다.
- 서로 다른 날짜의 후속 결정·취소·변경은 별도 관측으로 남긴다. 비슷하다는 이유로 지우지 않는다.
- 코드가 같은 기사·같은 정규화 문장 중복을 제거한다. 다른 기사 간 의미 중복은 우선 검색 후보를 묶어 같은 내용을 반복 전달하지 않는 방식으로 다룬다. 별도 중복 판정 LLM은 추가하지 않는다.

## 5. 어떤 부분에 설명이 필요한가

### 5.1 질문 선정 기준

Terra가 현재 관측과 흐름 초안을 보고 초보자의 이해를 막는 지점을 질문으로 만든다. 완성된 요약을 만들고 다시 읽는 별도 호출은 두지 않는다. 최종 본문에 실제로 등장하는 내용과 질문이 맞는지도 사용자 평가에서 확인한다.

초기 관점은 다음과 같다.

- **행동의 이유:** 왜 그 주체가 그 결정을 했는가?
- **중간 과정:** A가 변하면 어떤 과정을 거쳐 B에 영향을 주는가?
- **뜻밖의 결과:** 규모가 늘었는데 왜 시장 반응은 부정적인가?
- **읽는 데 꼭 필요한 개념:** 해당 연결을 이해하려면 어떤 용어를 풀어야 하는가?

이를 질문 개수 할당표로 사용하지 않는다. 쉬운 사실을 다른 말로 반복하는 질문, 흐름과 관계없는 배경 상식, 이미 본문에서 충분히 답한 질문은 줄인다. 한편 ‘고용이 감소했다’는 이해되더라도 ‘기저효과’는 별도 설명이 필요할 수 있으므로, 고용 분야 전체를 쉬운 주제로 취급하지 않는다.

사용자 피드백으로 질문의 목적을 경제 이해로 한정한다. 낯선 장비의 기술적 기능, 미공개 사양·물량·배분 기준을 채우는 질문, ‘생산에는 재료·인력·돈이 필요하다’는 준비물 나열은 제외한다. 구체적 제약이 비용·공급·가격·선택을 바꾸는 과정은 설명 대상으로 남긴다. 전문가에게 당연한 가격 형성·금융 수단의 기초 관계까지 생략한다는 뜻은 아니다. `reason`은 원문 정보의 부재보다 독자가 모르는 경제 개념·전달 과정을 설명한다. 정의 질문에 세부 사업 내역·집행 조건 확인까지 묶지 않는다.

관측마다 질문을 붙일 의무는 없다. 저장할 사건의 가치와 별도로 풀어 설명할 필요성을 구분한다. 구매·전달 절차를 되풀이하거나 생산 물량이 늘면 공급 가능 물량도 늘어난다고 바꿔 말하는 것만으로는 경제 학습 가치가 생기지 않는다. 이 기준을 최종 질문 선정에도 적용하며 필요한 질문의 개수를 고정하지 않는다.

질문의 필요성과 답할 근거의 존재는 별개다. 근거가 없을 것 같다고 필요한 질문을 처음부터 제외하면 안 된다. 필요한 질문은 남기고, 답할 수 있는 범위를 다음 단계에서 판정한다.

### 5.2 기존 설계 출력에 추가할 내용

각 흐름에 `questions`를 추가한다. 질문별로 연결되는 현재 관측 ID, 질문 문장, 짧은 선정 이유, 필요한 경우의 검색 요청을 함께 반환한다. 선정 이유는 평가·trace용이며 화면에 노출하지 않는다.

검색 요청은 경제원리용 문장과 기사 검색용 문장·대상 단어로 제한한다. 이미 현재 근거로 충분하면 검색 요청을 비운다. 별도 검색 계획 LLM이나 영구 엔티티 그래프는 만들지 않는다.

예를 들어 ‘구글이 왜 핀란드에 투자하나요?’의 검색에는 구글·핀란드·해당 데이터센터 투자 결정이 들어가야 한다. ‘투자 이유’만 검색하거나, 모델이 상상한 이유인 ‘저렴한 전력’부터 검색해 확인 편향을 만들지 않는다. 대상 단어는 현재 기사에 확인된 표현을 사용한다. 표기 변형 누락은 사례가 확인된 뒤 보완한다. 회사가 같아도 사업이 다르면 같은 결정으로 취급하지 않는다.

## 6. 과거 기사와 원리를 어떻게 꺼내는가

### 6.1 질문별 검색

1. 현재 흐름이 이미 확보한 관측과 원문 근거를 먼저 확인한다.
2. 경제원리 질문은 질문·전달 경로를 임베딩해 기존 원리 DB에서 검색한다.
3. 사건 배경 질문은 `memory_eligible=true`인 과거 관측을 대상으로 단어 일치와 벡터 검색 후보를 함께 구한다. 회사·국가·정책·사업명 등 대상 일치 후보를 우선한다.
4. 관련 기사의 다른 관측과 실제 근거 문단도 함께 확인한다. 이전의 ‘한 과거 기사당 관측 하나’ 규칙 때문에 결정만 남고 이유가 탈락하지 않게, 질문에 필요한 소수 문단을 기사 단위로 묶는다.
5. 기억에 답이 없을 수 있으므로 기사 목록의 제목·요약도 검색한다. 벡터 점수가 높다는 사실만으로 충분한 근거라고 판단하지 않는다. 질문의 현재 기사를 먼저 확인하고, 대상이 일치하는 기사 목록 후보는 관측 후보와 함께 제한적으로 확인한다.
6. 질문의 현재 기사를 먼저 확인한다. 근거 가능한 원문이 2,000자 이하이면 전체 문단을 확인하고, 긴 기사는 대상 단어 일치 수로 정렬해 최대 6문단 복사한다. 동점은 원문 순서다. 원문 관측이 없는 경우에도 추가 추출 호출은 하지 않는다. 이 단순 순위가 이유 문단을 놓치는지 사용자 정답 문단으로 평가한다.
7. 코드가 중복을 제거하고 질문별 ID·기사·시점·근거 문단 묶음을 편집기에 보낸다.

단어 검색은 기존 PostgreSQL에서 매개변수화한 부분 일치 검색으로 시작한다. 벡터 후보와 합친 후 단어 일치·벡터 순위·기사 중복을 사용해 정렬한다. 한국어 형태소 분석기, 별도 검색 서버, 재순위 LLM은 첫 버전에 넣지 않는다. 후보 순위가 틀리는 실제 사례가 쌓이면 그 검색 단계만 수정한다.

기존 관측 벡터용 유사도 하한을 질문 벡터에 검증 없이 그대로 적용하지 않는다. 실제 질문별 정답 문단이 후보에 들어오는지 측정한 뒤 하한과 후보 수를 정한다.

`remember=false`는 일반적인 장기 검색 후보에서 제외한다는 뜻이다. 이후 구체적인 질문의 정답이 그 기사 원문에 있다면 새로 검증해 사용할 수 있다. 원문 검색 결과는 답변 후보로만 쓰며, 검색됐다는 이유만으로 장기 기억에 자동 승격하지 않는다.

### 6.2 시간과 대상의 일치

- 9월 10일 평가의 현재 분석창은 9월 9일 05:00 이상~9월 10일 05:00 미만이다. 과거 후보는 분석창 시작 이전이며, 현재 창의 관련 기사와 분리해 전달한다.
- 발표일과 실제 시행일·측정기간은 다를 수 있다. 발행일만으로 인과관계를 판단하지 않고 관측문에 보존한 사건 시점·기간을 함께 읽는다.
- 과거 계획을 현재의 실행 완료로 바꾸지 않는다. 같은 대상의 후속 변경·철회 후보도 제한된 기사 검색에 포함한다. 시간상 이후라는 이유만으로 다른 사업의 발표를 덮어쓰기 근거로 쓰지 않는다.
- 과거 비교에 사용할 날짜·제목·URL은 추출 당시 `source_snapshot`과 일치해야 한다. 현재 `articles.published_at`이 개정으로 바뀌었다고 과거 기억의 시점이 바뀌어서는 안 된다.
- 과거 날짜를 시험할 때 그 날짜 이후의 기사·수정본으로 답을 보충하지 않는다. 당시 원문을 확보하지 못했고 현재 페이지의 수정 이력도 확인할 수 없다면 ‘당시 자료 재현 불가’로 남긴다.

과거에 이유를 설명한 기사가 있었을 수 있다는 기대는 근거가 아니다. 기사 미수집, 본문 미확보, 추출 누락, 검색 실패를 서로 다른 원인으로 기록한다. 원문을 복구할 수 없는 경우까지 LLM으로 해결한다고 약속하지 않는다.

## 7. 답변 작성과 근거 경계

최종 Luna 호출은 흐름별 본문과 질문·답변을 함께 쓴다. 문장 수보다 이해에 필요한 중간 과정과 출력 토큰 상한을 기준으로 길이를 조절한다. 질문·답변은 클릭 없이 본문 아래 보이며, 출처의 상세 문단은 접어서 볼 수 있다.

답변은 먼저 질문에 직접 답하고, 이어 필요한 중간 과정을 쉬운 말로 설명한다. 용어는 처음 나올 때 풀어 쓴다. 일반적인 조건과 기사에서 확인된 결과를 구분한다. 원리 설명의 숫자 예시를 임의로 만들거나, 발표한 최대 매입 한도를 실제 집행 금액으로 바꾸지 않는다.

일반 원리는 경제원리 DB를 우선한다. 원리에 대한 검색 결과가 없을 때는 사용자의 의도에 따라 LLM이 널리 쓰이는 기초 원리를 조건부 일반론으로 설명할 수 있다. 이 경우 ‘일반적으로는’과 같은 표현으로 범위를 명확히 하며, 기사나 원리 DB가 뒷받침한 것처럼 출처를 붙이지 않는다. 해당 설명은 평가에서 별도 확인하고 사건 기억으로 저장하지 않는다.

특정 기업·국가의 목적, 사건 원인, 과거 수치, 시장 기대는 실제 기사 근거가 필요하다. 구글이 AI 서비스를 위해 투자했다는 근거만으로 다른 국가 대신 핀란드를 선택한 결정적 이유까지 확정하지 않는다. 일반적인 입지 장점을 실제 선택 이유로 바꾸지 않는다.

질문별 답변과 사용한 관측·원리·문단 ID를 반환한다. 설명 가능한 개념·경제 작동 과정을 설명한 뒤 끝낸다. 일반 원리를 설명하면서 독자가 묻지 않은 특정 설비·수량·집행 여부의 부재까지 매번 덧붙이지 않는다. 일반적인 조건은 조건문으로, 계획·한도는 계획·한도로 표현해 사실의 범위를 지킨다. 질문의 핵심이 특정 결정의 실제 이유·수치인데 근거가 없을 때만 해당 한계를 짧게 밝히고 추측으로 채우지 않는다. 검색 실패·근거 부족은 평가 기록에 남기며 화면을 자료 부족 안내로 채우는 것은 성공이 아니다.

새로 확인한 원문이 흐름 설계의 핵심 사실과 충돌하면 편집기가 조용히 설계를 바꾸거나 둘을 섞지 않는다. 해당 흐름·근거 ID가 담긴 `conflicts`를 반환하고 그 revision을 공개하지 않는다. 충돌은 trace에 남겨 설계 또는 원문 추출 단계에서 수정한다. 자동 재작성 체인은 두지 않는다.

### 7.1 코드 검증

- 질문·답변이 계획의 흐름과 순서에 연결되는지, 필요한 질문을 조용히 삭제하지 않았는지 검사한다.
- 답변별 사용 ID가 그 질문에 전달한 허용 근거인지 검사한다. 다른 흐름의 근거가 있다는 이유로 통과시키지 않는다.
- 수치 검사는 해당 답변에 허용된 원문·관측·원리 기준으로 한다. LLM이 만든 질문·connection의 숫자를 원천 근거로 인정하지 않는다.
- 원문 문단 ID와 저장된 문단 텍스트의 일치를 보존한다. URL·날짜는 코드가 결합한다.
- coverage·구조·근거 ID·수치 검증이 실패하면 공개하지 않고 이전 SUCCESS를 유지한다.
- `conflicts`가 비어 있지 않으면 FAILED로 기록한다. 이 신호는 모델이 감지한 충돌이며, 빈 배열이 의미 오류가 없다는 증명은 아니다.

이 검사는 의미 전체의 참·거짓 판정이 아니다. 그럴듯한 잘못된 인과, 시점 혼동, 원문이 지지하지 않는 답은 사용자 비교 평가에서도 점검한다. 별도 검증 LLM은 추가하지 않는다.

## 8. 사용자 판단과 모델 판단을 맞추는 과정

### 8.1 두 평가를 따로 진행한다

| 평가 | 사용자에게 보여줄 것 | 사용자가 알려줄 것 | 비교 결과 |
|---|---|---|---|
| 질문 선정 | 고정 본문/흐름 초안, 모델 질문, 짧은 선정 이유 | 추가로 궁금한 점, 불필요한 질문, 원하는 질문 범위 | 필요한 질문 누락·불필요한 질문·질문의 범위 차이 |
| 기억 선정 | 기사 원문 문단, 모델이 남긴 정보와 남기지 않은 부분, 선정 이유 | 기억할 정보, 사소한 정보, 빠진 목적·조건 | 유용한 기억 누락·사소한 기억 채택·추출 왜곡 |

모델이 고른 정보만 보여주고 ‘괜찮나요?’라고 묻지 않는다. 질문 평가는 본문 전체에서 추가할 질문을 받을 수 있게 하고, 기억 평가는 원문에서 모델이 놓친 문단을 지목할 수 있게 한다. 전체 기사에서 원문 후보로도 선택되지 않은 기사 표본도 함께 확인해 앞단의 누락을 잡는다.

사용자가 고른 기사만으로 기억 평가를 하면 이미 중요한 기사에 편향된다. 선별 통과 기사, 탈락 기사, 경계 사례, 새 정보 없는 반복 보도를 섞고, 표본 선택 규칙·대상을 기록한다. 필요하면 일부 사례는 모델 결정을 보기 전에 사용자 판단부터 받아 비교한다.

### 8.2 사용자는 자연어로 피드백한다

예: ‘Q02는 없어도 돼’, ‘유가가 왜 상품 가격까지 올리는지가 궁금해’, ‘M03은 사소해’, ‘이 기사에서 투자 이유는 꼭 남겨야 해’처럼 말하면 된다. 사용자가 점수표·JSON·분류 코드를 직접 작성할 필요는 없다.

Codex가 원문 피드백을 보존하고 다음 기록을 작성한다.

1. 사용자가 원한 판단과 그 이유
2. 모델이 실제로 한 판단
3. 같은 뜻인 표현 차이인지, 실제 판단 차이인지
4. 최초로 차이가 생긴 단계와 근거
5. 수정할 일반 규칙과 최소 변경
6. 같은 입력의 변경 전후 결과·사용 토큰·남은 오류

질문 선정의 기준은 사용자의 독자 관점이다. 사건 사실의 기준은 출처다. 사용자가 궁금해한다는 이유만으로 기사에 없는 사실이 생기지는 않으므로, 필요한 질문을 유지하면서 근거 부재를 별도로 보고한다.

### 8.3 한 번의 반복

```text
고정 자료로 모델 실행 → 비교표 제시 → 사용자 피드백
  → 기준 사례에 사용자 판단 기록
  → 최초 실패 단계 진단
  → 해당 규칙·프롬프트·검색 조건만 수정
  → 동일 자료로 재실행
  → 다른 날짜의 미사용 자료로 회귀 확인
  → 개선·퇴행·비용 차이를 사용자에게 제시
```

새로운 사용자 판단을 받을 때마다 이 절차를 반복한다. 의미가 다른 피드백을 임의로 합치거나 사용자가 말하지 않은 선호를 정답으로 확정하지 않는다. ‘AI도 같은 단어를 썼는가’보다 같은 이해의 빈칸을 짚었는지 비교한다.

### 8.4 실패 소유 단계

| 차이 | 우선 수정할 곳 |
|---|---|
| 중요한 배경 기사가 원문 후보에 없음 | 제목 사전선별·기사 정밀선별 |
| 원문에 이유가 있는데 관측에 없음 | 관측 추출과 길이·개수 상한 |
| 이유를 추출했지만 기억하지 않음 | 기억 선정 기준 |
| 사소한 관측을 기억으로 승인 | 기억 선정 기준 |
| 사용자가 궁금한 질문을 생성하지 않음 | Terra 질문 선정 |
| 같은 사건을 묻는데 다른 사업을 검색 | 검색 요청의 대상·검색 조건 |
| 정답 문단이 DB에 있는데 후보에서 탈락 | 검색 순위·후보 수·문단 묶음 |
| 후보에 정답이 있는데 답변에서 누락·왜곡 | 최종 Q&A 작성 |
| 본문이 딱딱하거나 중간 과정이 생략됨 | 최종 편집 |
| 원문에 근거 자체가 없음 | 수집·자료 부족으로 기록, 추론으로 메우지 않음 |

### 8.5 평가 지표와 통과 기준

질문 평가와 기억 평가 모두 ‘모델이 선택한 것 중 사용자가 필요하다고 본 비율’과 ‘사용자가 필요하다고 본 것 중 모델이 선택한 비율’을 함께 본다. 이를 통해 모두 고르는 모델과 거의 버리는 모델을 구분한다. 평가 대상이 0개이면 해당 비율은 평가 불가로 표시한다.

추가로 다음을 보고한다.

- 질문별 답변에 필요한 정답 문단이 검색 후보에 포함됐는지
- 질문에 직접 답했는지, 중간 과정이 이해되는지, 미해결 이유가 무엇인지
- 사실·시점·주장 강도 오류, 불필요한 기억과 반복 문장의 수
- 단계별 API 호출·입출력 토큰·캐시·추정 비용

사용자 기준 질문은 뜻 단위로 대응시키며 1:1·분할·병합 대응을 기록한다. 단순 문자열 일치나 다른 LLM의 채점만으로 통과시키지 않는다. 기억 평가의 정답 범위는 전체 기사·문단을 사용자와 확인한 사례에 한정하며, 표본 결과를 전체 DB의 품질 수치로 과장하지 않는다.

처음부터 임의로 ‘90점이면 완료’라고 정하지 않는다. 첫 평가에서 필요한 질문과 기억의 기준을 만든 뒤, 사용자가 수용할 누락·불필요 항목 수준을 정한다. 사실 왜곡·출처 오류·미래 자료 혼입·예산 초과는 허용하지 않는다. 프롬프트 수정에 사용하지 않은 다른 고정 날짜 2개 이상에서도 유지돼야 운영 후보가 된다.

이 상태에서 자동 운영을 시작하고, 새 실패가 발견되면 사례를 추가해 반복한다. 완벽한 일치나 모든 미래 질문에 대한 답변 가능성을 보장하지 않는다.

### 8.6 피드백을 어디에 남기는가

첫 단계는 저장소의 Markdown 평가 기록과 로컬 고정 JSON 자료로 충분하다. 별도 라벨링 서비스·관리자 UI·평가 DB는 만들지 않는다.

- 공개 가능한 기준과 선정 예시는 `docs/ECONOMIC_FLOW_BEGINNER_MEMORY_REVIEW.md`에 기록한다.
- 실행별 고정 입력·전체 원문·모델 출력·사용자 판단·usage는 git에서 제외된 `pipeline-debug/beginner-memory/`에 저장한다. 대화에만 의존하지 않는다.
- 각 실험은 날짜·분석창·입력 해시·기억 DB 스냅샷·원리 후보·모델/프롬프트/검색 버전을 묶어 보존한다.
- 사용자 정답과 모델 결과는 별도로 저장한다. 새 실행이 이전 정답·결과를 덮어쓰지 않는다.
- 피드백 전체를 매일 프롬프트에 넣지 않는다. 반복되는 판단 차이를 일반 규칙으로 정리하고 필요한 짧은 예시만 포함한다. 전체 사례는 회귀시험에서 사용한다.

## 9. 토큰과 비용 관리

새 정보 저장은 기존 선별·추출 호출, 질문 선정은 기존 Terra 호출, 답변 작성은 기존 Luna 호출을 확장한다. 원문과 최종 글을 여러 모델에 반복 전송하지 않는다.

다음은 첫 실험의 상한 제안이며 품질 통과가 확인된 운영 설정은 아니다.

| 항목 | 초기 방침 |
|---|---|
| 전체 일일 비용 | 기존 USD 0.14 유지. 자동 증액하지 않음 |
| 일일 새 원문 선별 | 브리핑·기억 기사 합집합 최대 20개, 오늘 필수 기사 우선 |
| 질문 검색 | 중복 제거 후 추가 검색이 필요한 질문 최대 8개, 일괄 임베딩 |
| 과거 후보 | 질문당 상위 3기사, 최종 전달은 전체 최대 8기사·합계 8,000자 안에서 문단 단위 축소 |
| 경제원리 | 기존 최대 4청크·합계 4,000자에서 시작 |
| 미확보 원문 수집 | 실행당 최대 3기사. 과거 날짜의 재현에서는 현재 웹페이지로 보충하지 않음 |
| 설계/편집 출력 | 기존 4,000/6,000토큰에서 먼저 시험 |
| 반복 검색·자동 재작성 | 없음. 네트워크 재시도는 기존 규칙 적용 |

질문 수와 흐름 수는 위 검색 횟수로 고정하지 않는다. 현재 근거만으로 답할 질문에는 추가 검색이 필요 없다. 상한에 걸린 질문을 불필요하다고 표시하거나 조용히 버리지 않고 ‘예산으로 미검색’으로 기록한다. 필수 질문이 계속 미해결이면 비용 안에서 입력·출력 배분을 바꿔 비교한다. 출력 부족으로 필수 흐름이 탈락하면 성공 처리하지 않는다.

각 호출 직전에 누적 사용량, 이번 입력 추정치·최대 출력과 후속 단계 여유 예산을 합산한다. 선별·추출에서는 USD 0.09, 설계·질문 임베딩에서는 USD 0.015를 예약하고 최종 편집 전 다시 계산한다. 성공 처리 전 실제 usage 기준 상한도 검사한다. 추가 검색·추출·편집 입력도 합산한다. 추가 처리가 불가능하면 가능한 근거 범위에서 답변하거나, 최종 결과 자체를 정상 생성할 예산이 없으면 기존 실패 규칙을 따른다. 캐시는 같은 원문·프롬프트·모델·검색 기준에서만 재사용한다.

평가 비용과 운영 1회 비용을 분리한다. 한 단계의 수정 시험에 수집·선별·전체 원문 추출을 다시 돌리지 않는다. 질문 수정은 질문 선정 이후만, 기억 선정 수정은 해당 고정 원문만 시험한다. 테스트를 여러 번 하는 누적 비용도 따로 기록하고, 실험 예산을 소진하면 결과를 보고한 후 다음 범위를 정한다. 테스트를 이유로 일일 비용 가드를 끄지 않는다.

## 10. 첫 시험과 적용 순서

### 10.1 설계 뒤 첫 시험

9월 10일 화면과 그 결과에 사용한 기사·원문·관측·가능한 usage/trace를 읽기 전용으로 고정한다. 운영 화면과 로컬 DB가 같은 자료라고 가정하지 않는다. 로컬에는 9월 11일 실행 자료가 확인됐으므로, 정확한 9월 10일 trace를 확보하지 못하면 화면·출처로 관찰한 문제와 내부 단계에 대한 가설을 구분한다.

첫 질문 정답 후보는 사용자가 이미 준 일곱 질문이다. 사용자 요청에 따라 먼저 구현하고, 국채 바이백 기사 한 편의 원문을 고정해 실제 실행했다. 원문·모델 질문·기억 후보·답변을 함께 보여 사용자에게 남길 것·버릴 것·빠진 것을 받는다. 다음 기사는 첫 피드백 반영 뒤 진행한다. 사용자가 아직 정하지 않은 기억 기준을 미리 승인된 정답으로 취급하지 않는다.

첫 기사 전체 실행 이후 개선 시험은 다음 순서로 분리한다.

1. 같은 흐름·현재 관측을 고정하고 질문 선정만 시험한다.
2. 같은 기사 원문을 고정하고 기억 선정만 시험한다.
3. 사용자가 필요하다고 판단한 질문과 기억으로 검색을 시험한다. 생성 오류가 검색 평가를 가리지 않게 한다.
4. 개선한 모델의 실제 질문·기억 출력을 연결해 전체 결과를 시험한다.
5. 다른 날짜 2개 이상에서 근거성·누락·불필요한 설명·비용 회귀를 확인한다.

금리·물가·고용, 투자·공급망, 원인 설명이 없는 기사, 취소·변경된 계획, 같은 기업의 다른 사업, 사소한 홍보 기사를 포함한다. 9월 10일 사례만 잘 답하도록 프롬프트를 맞추지 않는다.

### 10.2 구현과 공개

사용자의 구현 요청에 따라 코드와 V26 migration을 먼저 구현했다. 사용자 비교로 기준을 정리하는 단계는 이제 시작한다. 평가 중의 기억 후보는 운영 장기 기억에 자동 적재하지 않는다. 검증된 기준·자료·버전으로 전환하고, 그 뒤부터 정상 운영에서는 모델이 자동 선별한다. 매일 모든 항목을 사용자가 승인해야 하는 구조를 만들지 않는다.

V2 구현 계약은 운영 가이드의 V2 항목과 이 문서에 기록했고, V1 프롬프트 문서에서 연결했다. 최초 적용은 기능별 테스트와 고정 날짜 재실행을 거친다. 9월 10일 공개 결과는 검증된 새 revision으로 업데이트하며 기존 성공본을 보존한다. 설계 작성 자체가 코드 적용·브리핑 수정·배포를 의미하지 않는다.

## 11. 첫 버전에서 만들지 않는 것

- 경제 노드·관계 그래프, 개별 기사별 종합 분석기, 관계 분류·검증 LLM 체인
- 모든 수집 기사 원문 선행 수집과 전체 임베딩
- 중요도 점수·복잡한 분류 체계·자동 모델 승격
- 반복적인 검색·재작성 에이전트, 일반 웹 전체의 자동 백필
- 사용자 피드백을 매일 전부 입력하는 긴 프롬프트
- 파인튜닝, 별도 벡터 DB·검색 서버·라벨링 서비스

추가 기능은 고정 자료에서 기존 방법의 실패를 확인하고, 그 기능이 해당 실패를 개선하는지 비용과 함께 검증한 뒤 도입한다.
