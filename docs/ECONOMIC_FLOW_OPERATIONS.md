## 2026-09-16 거시경제 선별 변경 — 로컬 검증, 미배포

이번 사용자 범위는 물가·성장·통화정책·시장금리·신용·환율·자금 흐름의 판단을
갱신하는 경제 흐름이다. 아래 과거 버전 기록 중 별도 전략기술·구체적 산업·기업 이슈를
포함하라는 기준보다 이 범위를 우선한다. 다른 기업·산업 기능을 삭제하는 변경은 아니다.

`daily-flow-v2.7-macro`는 제목 후보 회수 → 기존 정밀선별 호출 → 기존 추출·설계·편집을
유지한다. 제목 단계의 분야 차단 없이 거시 근거를 회수하고, 개별 기업·업종·행사와
일반적인 정책 의지를 거시 표현으로 포장하여 선정하거나 기억 부록에 넣지 않는다.
같은 지표의 숫자가 겹쳐도 별도 원인·반대 경로·전파 시차는 보존한다. 가격 격차의 재진술에
원문에 없는 금융 경로를 붙여 중요도를 높이지 않으며, 구체적 변경·새 판단 근거가 없는
정책 기조 재확인과 설명이 중복된 후행 가격 반응을 제한한다.
정밀선별은 같은 모델·2,500 출력 토큰 상한 안에서 reasoning을 low에서 medium으로
높였다. 낮은 검토 강도에서 업종 비용·수익성 기사를 거시 물가로 포장해 선택하는 회귀가
재현됐기 때문이다. 제목 선별·추출·설계·편집의 모델과 검토 강도는 유지한다.

RSS 첫 문장만으로 본문의 다른 정책 해석을 구분하지 못한 재현 사례 때문에,
**제목 사전선별을 통과한 후보에 한해서** 원문을 확보한다. 기존 정밀선별 입력에
기사당 최대 900자, 전체 발췌 최대 45,000자의 완전한 문단을 그대로 복사한다. 후보가
많으면 기사별 문단 예산을 나눠 설계 비용 여유를 보존한다. 선두 문단과 관계 설명을 우선
배치하고 원문 순서를 복구한다. 이는 제한된 발췌이며 의미적 완전성을 보장하는 검증기가
아니다. 원문 전체를 모든 단계에 보내거나 별도 요약·검증 LLM을 호출하지 않는다.
원문은 이후 선택 기사 추출에서 재사용한다. 기존 최대 20개 추출·모델·출력 한도는 유지한다.

전체 재실행에서 새로 선택한 의사록·통계의 시점이 관측과 본문에서 빠지고, 거시 기사에
딸린 품목·업종 세부가 별도 질문으로 확장되는 오류를 확인했다. 설계·편집은 동일한 거시
범위를 문단과 질문에도 적용하고 편집에서 원문의 회의 시점·측정기간을 명시한다. 거시 악재와
비교한다는 이유로 개별 기업 실적·업종 상대강세 관측을 선택하지 않으며, 설계의
observationIds와 질문 근거에서 제외한다. 추출
v6~v11의 전체 추출 변경은 시점 혼동·불필요한 날짜 추가·별도 근거 누락을 일으켜 채택하지
않았다. 현재 `observation-memory-v13-scope`는 유효 원문 앞 3개 문단에 의사록이 있는
경우에만 대표 관측의 회의 시점 보존 지침을 추가한다. 계약통화 표현이 있는 기사에서는
전체/품목 범위를 섞지 않고 통화 기준을 비교하도록 보완한다. 나머지는 기존 v5 추출 지침을 유지한다.
짧은 도입부로 자료 성격을 판단하는 방식이므로 의사록임이 뒤늦게 나타나는 기사는 이 추가
지침을 받지 못할 수 있다. 설계에서 확인된 환율/통화가치 방향 및 가격/물량 비교 혼동도
해당 단계에서 보완했다. M1에서 정기예금으로의 이동을 M2 총량 증가와 동일시하지 않도록
설계·편집에서 부분/전체 관계를 구분한다. 지표 발표와 정책 결정의 전후 관계를 질문의
전제에도 적용하고, 공통 전달 경로가 없는 가계 한도·국가 재정을 부채라는 이름만으로
한 흐름에 묶지 않는다. 편집 소제목의 정책 유인/제약 방향과 전체/품목 지수의
비교 범위도 원문과 일치시킨다. 본문과 답변 소제목에서 금리 차 축소의 제약을
비교 대상보다 금리가 낮아지기 어렵다는 대소관계로 바꾸지 않는다.
스프레드·금리 차 질문이 있는 편집 묶음에만 상세 비교 지침을 적용한다. 무관한
재정 답변의 소제목이 변하는 회귀가 재현돼 적용 범위를 좁혔으며, 일반 비교 보존
규칙은 유지한다. 해당 단어 없이 표현한 질문은 상세 지침을 받지 못할 수 있다.
과거 발언의 실제 시점이 원문에 있으면 남기되,
없을 때는 발행일로 발언일을 만들어 채우지 않고 기사에서 전한 견해로 소개한다. 편집의
분량 축약 지침에서도 과거 회의 시점·측정기간은 행사 일정과 구분하여 첫 소개 문장에 남긴다. 숫자 검증은 기존 비수량 표현인 ‘제3국’의 ‘이에요’ 종결형과
‘이나’ 조사를 인식하도록 좁혀 수정했다. 실제 3%·3개월·3개국 등 수량 검증은 유지한다.
편집 입력의 `flowNumbers`·`questionNumbers`에는 같은 검증 함수가 계산한 해당 범위의
허용 숫자만 제공한다. 다른 질문의 연도·만기를 가져오는 실패를 줄이기 위한 입력 보완이며,
인용 가능한 관측을 늘리거나 검증기를 완화하는 기능은 아니다. 입력 증가도 기존 비용 가드에 반영한다.
새 분석 단계나 검증 LLM은 추가하지 않았으며 최종 품질 판정은 아래 보고서를 따른다.

정밀선별 비용 사전 검사는 발췌까지 포함한 실제 입력으로 계산한다. 일일 USD 0.14,
추출 100,000 tokens, 설계·편집 입력 및 출력 한도, 문단·숫자·인용 검증은 그대로다.
HTTP 원문 조회 수와 정밀선별 입력은 늘 수 있으므로 실제 usage와 실패를 함께 확인한다.
신규 원문은 페이지의 송고·수정 시각이 모두 마감 전인지 확인하고, 시간 미확인이나
마감 이후 판본이면 사용하지 않는다. 원문 확보 실패는 관련성 탈락으로 간주하지 않는다.

추가 trace: `prefilterRounds`(6시간/병합 단계 선택 ID), `hardSignalRescuedArticleIds`,
`selectionEvidenceHashes`, `selectionBodyUnavailableArticleIds`. 강제 회수는 사전 후보만
복원하며 정밀선별을 통과시킨다는 뜻이 아니다. 수집 분야를 일괄 차단하지 않는다.

## 1. 서비스가 달성해야 하는 것

이 서비스는 “기사 몇 개를 쉽게 요약하는 서비스”가 아니다. 매일 직전 24시간의 전체 뉴스에서 경제적으로 중요한 관측을 찾아 다음을 하나의 흐름으로 설명해야 한다.

- 세계 각국과 기업·가계가 어떤 상황에 놓였는가
- 각 주체가 무엇을 얻으려 하고 무엇에 제약받는가
- 주체들이 협력·경쟁·대립하면서 비용과 이익을 어떻게 주고받는가
- 충격과 결정이 에너지·공급망·무역·투자·물가·금리·환율·고용으로 어떻게 번지는가
- 초보자가 이해하기 어려운 행동의 이유와 경제 전달 과정을 본문 아래 질문·답변으로 풀어 설명한다. ‘앞으로 확인할 것’은 표시하지 않는다.

흐름 개수는 정하지 않는다. 독립적인 경제 동인의 개수가 결과 개수를 결정한다. 같은 상류 충격을 국가별 기사로 쪼개거나 같은 AI 수요를 반도체·전력·자금조달 기사별로 나누면 실패다. 반대로 현재 근거에 공통 원인이 없는데 억지로 합치는 것도 실패다.

## 2. 운영 시간의 의미

모든 시간은 `Asia/Seoul` 기준이다.

```text
매시 05분  연합뉴스 RSS 전체 스트림 최근 26시간 수집
매일 05:10 전날 05:00 이상 ~ 당일 05:00 미만 기사 분석
```

예를 들어 `target_date=2026-09-11`은 `2026-09-10 05:00:00` 이상, `2026-09-11 05:00:00` 미만을 뜻한다. 05:10 실행으로 05:05 수집 완료 여유를 둔다. 시간별 수집은 AI를 호출하지 않는다.

설정:

```yaml
briefing.scheduler.collect-cron: 0 5 * * * *
briefing.scheduler.daily-cron: 0 10 5 * * *
```

V2.6의 26시간 범위는 재시작 때 RSS에 아직 남아 있는 직전 일일 창 기사를 회수하기 위한 것이다. 중복은 기존 기사 키로 처리하며, RSS에서 이미 사라진 기사나 PC 전원 중단 자체를 복구하지 않는다. 원문 복원이 필요한 과거 평가는 복원 입력과 실제 수집 입력을 구별한다.

잘못된 cron 하나는 그 작업만 비활성화하고 웹 서버를 내리지 않는다.

```text
  → 코드: coverage·허용 ID·순서·숫자 검증
  → 기사 URL과 원문 근거 문단을 결합해 공개
```

### 모델별 책임

| 단계 | 모델 | 책임 | 하지 않는 일 |
|---|---|---|---|
| 제목 사전선별 | Luna `low` | 원문을 확인할 가능성 높은 후보를 넉넉히 회수 | 원문 판단, 최종 중요도 판단 |
| 제목·요약 정밀선별 | Luna `low` | 최종 흐름에 독립적으로 필요하거나 다른 기사의 원인·반응·제약을 보태는 기사 확정 | 원문에 없는 사실 추정 |
| 관측 추출 | Luna `none` | 원문 관측·최소 근거 문단·장기 검색 여부·선정 이유 | 경제원리 추가, 기사 간 연결 |
| 흐름 설계 | Terra `medium` | 흐름 묶기, 이해에 필요한 질문과 근거 검색 요청 | 최종 제목·장문 작성 |
| 독자용 편집 | Luna `low` | 쉬운 ~요체 본문·Q&A, 질문별 허용 후보에서 근거 선택·시점과 조건 점검 | 흐름 합치기·나누기, 없는 사건 원인 창작 |

Terra 하나에 선별·검증·장문 작성까지 다시 맡기지 않는다. 별도 검증 LLM도 추가하지 않는다. 구조 검증은 코드가 한다.

9월 12일 반복 평가에서 `none` 편집이 명시된 조건을 여러 번 생략하거나 외국어를 섞어, 같은 Luna 편집 호출의 추론을 `low`로 올려 재검증한다. 별도 호출을 추가하지 않고 전체 출력·추론의 기존 12,000 tokens 한도와 USD 0.14 비용 가드를 그대로 적용한다. 품질·실제 비용은 날짜 평가 기록에 남긴다.

V2.2의 독자용 편집은 본문 `explanation`과 각 `answer`를 의미 단위로 나눈다. 주제나 설명의 역할이 바뀔 때 기존 문자열 안에 빈 줄(`\n\n`)을 넣고, 같은 흐름은 보통 1~3문장으로 묶는다. 문단 수를 채우기 위한 내용은 추가하지 않는다. V2.6은 각 문단 첫 줄에 `**한 문장 요약 소제목**`을 쓰고 다음 줄부터 본문을 쓴다. 소제목도 원문의 주체·시점·불확실성을 유지한다. 화면은 빈 줄을 실제 문단과 여백으로 표시하며, 문단 모양 때문에 재호출하거나 문장 수만으로 자동 분할하지 않는다. 호출 수·응답 스키마·비용 상한은 유지한다. V2.2 당시 사용자 지정 검증과 기존 결과 편집 범위는 2026-09-12 토트였다. V2.6의 추가 검증 범위는 9월 14일 학습 평가를 따른다.

V2.3은 기록적 숫자나 개별 기업의 행동 자체보다 경제적 전달 경로를 선별한다. 시장 종합을 개별 종가 기사로 대체하지 않고, 같은 전쟁이라도 다른 지역의 의존·제약·대체 선택은 중복으로 지우지 않는다. 개별 임금·파업·수주·지역 행사·금융상품은 광범위한 경제 영향 근거가 없으면 제외한다. 파업 전체를 금지하는 키워드 차단은 아니다. 추출은 기존 총 text 한도 660자(3×220자)를 유지하면서 **0~6개·각 220자 이하**로 배분한다. 짧은 관계가 세 관측 뒤에서 밀려나지 않게 하되 개수를 채우지 않는다. 추가 구조·근거 필드를 감안한 추출 출력 상한은 2,000 tokens이고 비용 사전 계산도 같은 상수를 쓴다. 숫자보다 이유·조건·반대 압력에 공간을 쓴다. 선별 이유는 읽기 우선순위이지 원문 증거가 아니므로 추출 입력에 다시 넣지 않는다. V2.6은 추출에서 제목도 중복 전송하지 않고 원문 문단 ID와 본문만 보낸다. 실제로 제공한 유효 문단 ID를 응답 스키마의 enum으로 제한해 범위형·가짜 ID를 차단하고, 기존 숫자·근거 검증도 유지한다.

## 4. 임베딩과 검색

현재 관측마다 `text-embedding-3-large`, 1,536차원 벡터를 한 번 만든다. 같은 벡터를 세 곳에서 재사용한다.

1. 과거 `article_observations` 상위 5개 검색
2. `economic_principle_chunk` 상위 2개 검색
3. 서로 다른 기사 관측 간 cosine 계산

과거 후보는 과거 기사 중복을 제거하고 현재 기사 하나에 최대 2개, 전체 최대 12개로 제한한다. runtime에서 반드시 “어느 현재 관측이 이 과거 관측을 검색했는지” 쌍을 보존한다. DB에는 그 임시 관계를 영구 저장하지 않고 `daily_briefings.trace_json.historyCandidatePairs`에 실행 추적만 남긴다.

기사 간 연결은 서로 다른 기사쌍마다 유사도가 가장 높은 관측 한 쌍만 남기고 cosine 0.30 이상인 상위 20쌍만 보낸다. 이는 Terra가 먼저 볼 후보이지 인과 근거가 아니다. 유사도만으로 경제적으로 연결됐다고 확정하지 않는다.

경제원리는 cosine 0.42 이상, 최대 4개, 본문 합계 4,000자까지 전달한다. 관련 원리가 없거나 기사 자체가 전달 경로를 설명하면 원리 0개가 정상이다. 과거 관측도 없으면 현재 관측만으로 정상 실행한다.

설계 단계에 실제 전달하는 원리는 완전한 청크 단위로 합계 1,500자까지 남긴다. 비용 압박에서 오늘의 원문 관계를 먼저 보존하기 위한 제한이며, 검색·질문 답변의 기존 최대 4개·4,000자 한도와 구별한다. 긴 청크를 문장 중간에서 자르거나 관련 없는 짧은 원리로 채우지 않는다.

설계 직전 남은 일일 비용에서 기존 최대 출력 6,000 tokens·후속 단계 예약액 USD 0.015·프롬프트 여유를 뺀 입력 예산을 계산한다. 필요한 경우 선택적 원문 문맥 예산을 500자씩 줄여 다시 배치한다. 모든 압축 관측은 유지하며 `plannerEvidenceCharsBudget`에 실제 문맥 한도를 기록한다. 선택적 문맥을 전부 줄여도 필수 입력이 넘으면 기존 비용 가드로 실패한다. 비용 상한을 올리거나 실제 usage를 할인하지 않는다.

과거 검색에는 `memory_eligible=true`이며 `source_snapshot`이 있는 관측만 넣는다. 기존 행은 자동 승인하지 않는다. 이전 `daily_briefings.result_json` 문장은 절대 넣지 않는다. 누적되는 기억은 원문 문단으로 추적 가능한 `article_observations`뿐이다.

정책·투자·행동 제안의 기억은 원문 전체에서 찾은 구체적인 이유와 대상 행동을 같은 `text`에 연결한다. 제안을 하지 않을 때의 손실·비용·선택 제약이 말미에 있더라도 핵심 이유를 보존하며, 비교 숫자나 실행 지연 요인이 그 이유를 밀어내지 않게 한다. 해당 이유 문단도 출처 스냅샷에 넣는다. `memoryReason`은 선정 이유일 뿐 검색용 본문이 아니므로 여기에만 사건 이유를 넣지 않는다. 기존 기억 개수·길이·출처 검증·비용 상한은 유지한다.

질문 설계에서는 핵심 대상·거래 방식·약어의 뜻과 이유·작동 과정을 함께 다룬다. 모든 압축 관측을 보존하고, 추가 원문은 기사별로 번갈아 배분한다. `currentEvidence`는 직접 근거이며 refs에 연결된 관측 ID를 표시한다. 해당 ID를 선택한 경우 그 직접 문단으로 압축된 이유·조건을 구체화할 수 있다. 이유·대조·조건 표현이 있는 직접 문단을 먼저 배치하며 직접 문맥은 7,500자, 직접·인접 합계는 8,500자 이하다. `currentAdjacentEvidence`는 원문 해시가 일치하는 앞뒤 한 문단으로, 별도 2,500자 한도와 남은 전체 문맥 한도를 함께 적용한다. 인접 문단은 질문 발견용이며 connection의 새 사건 근거나 장기 기억으로 승격하지 않는다. Terra 입력 15,000 tokens·비용 가드는 유지한다. 문맥 우선순위는 코드의 단순 표현 기반 순서이며 의미 보존을 보장하는 검증기는 아니다. 제한 밖 문단의 누락은 실제 결과로 계속 평가해야 한다.

질문은 경제 이해에 필요한 개념·연결로 한정한다. 일반 상식·장비 기능·미공개 세부 사항 채우기·당연한 생산 준비물 나열은 제외하며, 기초 가격 형성·금융 수단의 작동 과정은 유지한다. 답변은 설명 가능한 과정까지 설명하고 질문과 무관한 자료 부족 문구를 붙이지 않는다. 핵심 사건 이유가 불명일 때의 짧은 한계 표시와 계획·일반론·실제 결과의 구분은 유지한다. 이 지침은 캐나다 지원 기사 피드백을 반영한 로컬 평가 변경이다.

질문 검색은 별도로 질문당 상위 3기사, 실행 전체 8기사·8,000자까지 전달한다. 추가 검색 질문은 최대 8개로 제한하고 필요한 질문 자체를 삭제하지 않는다. 원리 예산은 실제 선택한 것 기준으로 4청크·4,000자다. 설계에서 버린 원리가 질문 검색 예산을 차지하지 않는다. 검색 문자열은 중복 제거해 일괄 임베딩한다. 편집 입력은 관측 ID별 `evidenceCatalog`와 중복 제거한 직접 문단 `sourceCatalog`를 연결한다. 문단 별칭 S는 인용 ID가 아니며 답변 권한은 각 Q의 `questionEvidence`·`questionPrinciples`가 결정한다. 본문은 `flowEvidence` 범위를 따른다. 같은 기사·본문 해시·문단만 공유하고 다른 판본을 합치지 않는다.

편집 입력이 15,000 tokens 안이면 기존처럼 한 번 호출한다. 넘으면 연속된 흐름을 가능한 크게 묶어 호출하며 해당 묶음의 질문·근거만 전달한다. 전체 F/Q ID·순서를 보존하고 최종 결과 전체를 기존 검증기로 검사한다. 단일 흐름도 상한을 넘으면 근거를 자르지 않고 실패한다. **전체 묶음에 배분하는 출력 상한의 합계가 12,000 tokens**이며 V2.6에서는 각 흐름의 본문 근거 관측 수와 질문 수에 따라 나눈다. 질문 수만 같은 두 흐름도 본문에서 설명할 관계가 많으면 더 큰 출력 몫을 갖는다. 각 호출에는 배정된 출력 한도에 맞춘 전체 한국어 분량 지침을 전달해 소제목과 답변의 반복을 줄인다. 호출별 입력·출력과 남은 출력 예약액을 일일 USD 0.14 가드로 검사한다. 이는 입력 초과 때의 분할이며 별도 재작성·검증 LLM 단계가 아니다. 호출 수와 입력 토큰은 늘 수 있으므로 `usage_json.stages.writer`의 총합으로 평가한다.

편집 응답 스키마도 실제 flowId·questionId와 질문별 인용 가능 ID로 제한한다. 흐름·질문별 anyOf 분기와 enum을 사용하고 빈 근거 목록은 빈 배열만 허용한다. 구조적으로 허용된 인용이 문장의 의미를 지지하는지는 별도 내용 평가가 필요하다. 기존 순서·중복·coverage·숫자·충돌 검증은 삭제하지 않는다. 지원 형식은 [OpenAI Structured Outputs 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)로 확인했다.

질문 기본 근거는 같은 흐름 전체가 아니라 설계자가 해당 질문에 명시한 현재 관측과 그 관측에 연결된 선택 과거 관측으로 제한한다. 예를 들어 장중 PPI 질문에 같은 흐름의 야간 CPI를 자동 제공하지 않는다. 설계자가 질문에는 명시했지만 상위 흐름 목록에 빠뜨린 **실재하는 현재 관측 ID**는 상위 목록에도 합쳐 일관되게 정규화하고 `questionEvidenceAdded`에 기록한다. 새 ID·기억·질문·인과를 만들지 않으며, 알 수 없는 ID와 질문의 과거 ID는 보정하지 않고 기존 검증에서 거절한다.

단어 검색은 PostgreSQL의 매개변수화한 AND 부분 일치다. 제목·요약 일치 후보와 과거 관측의 단어·벡터 후보를 합친다. 질문의 현재 기사를 먼저 확인한다. 근거 가능한 원문이 2,000자 이하면 온전히 확인하고, 긴 기사는 최대 6문단을 코드로 복사한다. 이미 전달한 근거 문단은 중복 전송하지 않는다. 본문 미확보 시 실행당 최대 3기사만 수집하고, 과거 날짜 재현에서는 오늘 웹페이지를 수집해 보충하지 않는다. 조회 문단은 장기 기억으로 자동 승격하지 않는다. 별도 추출·검증 LLM 호출은 없다. `questionSearches.principleCandidates`에서 검색 후보와 실제 전달된 원리를 구분한다.

## 5. DB 구조

경제흐름 핵심 테이블은 네 개다.

| 테이블 | 역할 |
|---|---|
| `articles` | RSS 메타데이터와 선택 기사 원문 |
| `article_observations` | 원문 근거 문단 ID가 붙은 관측과 임베딩 |
| `economic_principle_chunk` | 별도 빌더가 적재하는 경제원리와 임베딩 |
| `daily_briefings` | 날짜별 revision, 상태, 모델, usage, trace, 공개 결과 |

인증·환율 기능 때문에 `users`, `password_reset_tokens`, `exchange_rates`, `current_exchange_rates`는 유지한다. Flyway 이력을 포함한 정상 public 테이블은 총 9개다.

V26은 `article_observations.memory_eligible`(기본 false)과 `source_snapshot` JSONB를 추가한다. 스냅샷은 코드가 복사한 제목·URL·발행시각·본문 해시·원문 근거 문단이다. 근거 없는 기억은 DB 제약으로 거부한다.

V24는 구 분석·그래프·파이프라인 테이블 21개를 제거했다. V25는 입력 기사 0건을 `SUCCESS`로 오해하지 않도록 `NO_DATA` 상태를 추가했다. 적용된 Flyway 파일은 수정하거나 삭제하지 말고 항상 다음 번호의 새 migration을 만든다.

편집 응답의 flows 배열 길이는 해당 실행에서 Terra가 설계한 길이를 JSON Schema로 강제한다. 날짜별 흐름 개수를 미리 정하지 않는다. 질문 ID는 `Q03`과 `F02:Q03` 응답을 같은 로컬 ID로 정규화한 뒤 순서를 검증한다. 본문·답변의 수치와 질문별 근거 ID 검증은 유지하며 편집기가 새 수치 예시·단위 환산을 추가하지 않도록 지시한다. 답변에 쓴 수치가 질문에 허용된 다른 근거에 정확히 있으면 코드가 해당 근거 ID를 보완하고, 허용 근거 어디에도 없는 수치는 계속 실패시킨다.

V2.4의 로컬 검증 변경은 숫자 추출에서 확인된 비수량 표현 `제3의 통화`·`제3자` 안의 `3`만 제외한다. 띄어쓰기·조사와 단어 경계를 확인하며 `제숫자의` 전체를 면제하지 않는다. 같은 문장의 `3%`·`3개`와 날짜·순위·회차는 계속 검사한다. 본문·답변·인용 근거·경제원리·근거 ID 자동 보완에 같은 편집 단계 추출 함수를 사용하므로, 근거의 `제3자`가 답변의 `3개`를 뒷받침하거나 불필요한 인용을 추가하지 않는다. 관측 추출 단계·프롬프트·비용 가드·원문 문단 검증은 유지한다. V2.6의 9월 12일 재현에서 `제3국 기업`의 3이 수량으로 잘못 거절된 것을 확인해 `제3국`도 같은 경계 규칙에 추가했다. `3개국`·`제3국채`·같은 문장의 `3%`는 계속 검증한다. 새 비수량 표현은 실제 오탐을 확인한 뒤 좁게 추가한다. 배포는 별도다.

9월 14일 검증: `./gradlew clean test` 53개 통과·조건부 2개 제외. 고정 평가 `treasury_009_scoped_writer`(9월 11일)·`draghi_ai_004_reason`(9월 12일)의 저장 본문·답변과 실제 인용 관측·문단·원리 11쌍을 숫자 검증 단계에서 재검사해 변경 전후 오류 0건·숫자 토큰 변화 0건을 확인했다. 새 API 비용은 0이며 실행 스크립트와 결과는 git 제외 경로 `pipeline-debug/numeric-validation-20260914/`에 보존했다. 보고된 9월 14일 `F04:Q01`의 `제3의 통화` 표현은 회귀 테스트에 포함했지만, 로컬 DB에 해당 날짜의 usage·trace가 없어 실제 실패 run 전체를 재현한 것은 아니다.

상태 의미:

- `RUNNING`: 실행 중
- `SUCCESS`: 검증을 통과해 공개 가능한 결과. 흐름 0개도 가능하다.
- `FAILED`: API·예산·구조 검증 실패. 이전 성공 revision을 계속 공개한다.
- `NO_DATA`: 분석창에 기사 자체가 0건. 공개 대상으로 사용하지 않는다.

## 7. API

```text
GET /api/briefings/latest
GET /api/briefings/{yyyy-MM-dd}

```

관리자 Bearer token 필요:

```text
GET  /api/admin/briefings/runs?page=0&size=20&status=FAILED
```

수동 실행은 비동기이며 HTTP 202를 반환한다. 같은 프로세스에서 이미 실행 중이면 409다. 같은 날짜를 다시 돌리면 이전 행을 덮어쓰지 않고 revision을 올린다.

## 8. 비용·입력 안전장치

초기 운영 상한:

| 항목 | 상한 |
|---|---:|
| 제목 사전선별 추정 입력 | 50,000 tokens |
| 원문 관측 추출 추정 입력 | 100,000 tokens |
| Terra 입력 | 15,000 tokens |
| 전체 예상 일일 비용 | USD 0.14 |

기사 ID는 LLM 호출마다 짧은 별칭으로 바꾼다. 선별 시각은 `HH:mm`, 설계에서는 기사별 발행시각을 한 번 제공해 장 마감 이후 발표를 앞선 하락에 연결하지 않도록 한다. 제목 사전선별은 같은 6시간 안에서도 시간대별 기사를 교차 배열해 목록 위치 편향을 줄인다. 원문 전체는 선택된 기사의 관측 추출에 보내고 이후에는 근거 문단만 전달한다. 기사 ID·본문 해시·URL·발행시각·모델·추출 프롬프트 버전이 일치한 관측과 임베딩만 재사용한다. RSS 메타가 바뀌면 원문 상태를 무효화해 재수집한다. 추출 기준 변경 시 `EXTRACTION_PROMPT_VERSION`을 올린다. `trace_json.articleCountsByHour`에 분석창의 24개 시간대별 기사 수를 기록한다. 0건 시간대는 수집 확인의 단서이며 그 자체로 누락이나 실패를 확정하지 않는다.

호출 직전 입력·최대 출력 비용과 후속 단계 예약액(선별·추출 USD 0.09, 설계·질문 임베딩 USD 0.015)을 검사한다. 질문을 포함한 설계 출력 한도는 6,000 tokens이며 API 호출과 비용 사전 계산이 같은 상수를 사용한다. 2026-09-12 DEV 전체 날짜 실행에서 기존 4,000 tokens 출력이 잘려 JSON 파싱에 실패한 것을 반영했다. 최종 성공 전 실제 usage 비용 상한도 검사한다. 전체 일일 창의 V2 비용은 평가 중이다.

API가 반환한 정확한 usage와 코드에 설정된 단가 기반 추정 비용은 `daily_briefings.usage_json`에 기록한다. 가격이 바뀌면 계산식을 갱신하되 과거 usage 원본은 지우지 않는다.

```sql
FROM daily_briefings
```

그다음 최신 결과를 실제 독자 관점으로 읽는다.

- 경제원리는 사건 근거가 아니라 전달 경로 설명으로만 쓰였는가

## 11. 오류를 어느 단계에서 고칠지

| 증상 | 먼저 볼 값 | 소유 단계 |
|---|---|---|
| 기사 자체가 없음 | window count, RSS 로그 | 수집·시간창 |
| 중요한 제목이 사전 후보에 없음 | `prefilteredArticleIds` | Luna 제목 사전선별 입력·프롬프트 |
| 후보에는 있는데 최종 기사에서 빠짐 | `selectedArticleIds` | Luna 정밀선별 |
| 선택됐지만 관측이 없음 | `observationIds`, 기사 본문·span | 본문 파서·Luna 추출·코드 검증 |
| 근거는 좋은데 흐름이 기사별로 분절 | 최종 sources 묶음 | Terra planner |
| 서로 무관한 기사가 합쳐짐 | `connectionCandidates`, 관측문 | Terra planner·후보 packing |
| 흐름 구조는 맞고 문장만 어렵거나 강도가 틀림 | Terra connection과 최종 설명 | Luna writer |
| 관련 없는 과거가 사용됨 | `historyCandidatePairs`, `usedHistoryObservationIds` | 검색 packing·Terra planner |
| 원리가 억지로 붙음 | `principleChunkIds`, `usedPrincipleIds` | 원리 임베딩·하한·Terra planner |
| 필요한 질문 누락 | `plan[].questions`와 사용자 질문 대응 | Terra planner |
| 사소한 기억·목적 누락 | `memoryDecisions.raw/accepted`, 원문 | Luna extraction |
| 질문은 맞지만 정답 문단 없음 | `questionSearches`의 검색어·후보·전달 근거 | 질문 retrieval packing |
| 근거는 있지만 중간 과정 생략 | `writing`, 답변별 근거 | Luna writer |
| 토큰 급증 | stage별 usage와 기사/관측 수 | 해당 단계 입력 packing |

한 오류를 고치려고 모든 프롬프트를 동시에 바꾸지 않는다. 고정 날짜의 동일 입력으로 소유 단계만 바꾸고 이전 revision과 비교한다. 제목 누락을 Terra 프롬프트로 고칠 수 없고, 좋은 Terra 설계를 Luna가 어렵게 쓴 문제를 검색 구조로 고치면 안 된다.

## 12. 반복 개선 절차

1. 문제를 한 문장으로 정의하고 해당 날짜의 run ID와 실패 예시를 남긴다.
2. `trace_json`으로 최초로 잘못된 단계가 어디인지 찾는다.
3. 가능하면 저장된 기사·관측을 재사용해 그 단계 이후만 비교한다.
4. 같은 고정 입력에서 변경 전후의 누락, 거짓 인과, coverage, 비용을 함께 측정한다.
5. 한 날짜에서 좋아져도 다른 고정일 2개 이상에서 회귀가 없는지 본다.
6. 성공 기준을 통과한 뒤에만 운영 기본값을 바꾸고 prompt/pipeline version을 올린다.
7. 7일 usage 중앙값과 상위값으로 비용 상한을 조정한다.

과거 관측과 경제원리는 데이터가 쌓이면서 매일 별도로 평가한다. “사용 횟수가 늘었다”는 성공이 아니다. 과거는 현재만으로 알 수 없던 변화 방향을 정확히 보탰을 때, 원리는 기사 사이의 작동 경로를 정확히 설명했을 때만 성공이다.

## 13. 하지 말아야 할 것

- 흐름을 0~3개, 5개 같은 고정 개수로 제한하지 않는다.
- `statementKind`, `role`, `confidence`, `importance` 필드를 다시 만들지 않는다.
- source span을 의미 검증한다는 명목으로 별도 LLM validator를 붙이지 않는다.
- 모든 단계에 원문 전체를 다시 보내지 않는다.
- 모든 수집 기사 본문을 먼저 긁거나 모두 임베딩하지 않는다.
- 과거 최종 설명을 다음 날 사실 근거로 넣지 않는다.
- 경제원리 사용량을 높이려고 관련 없는 청크를 강제하지 않는다.
- 품질이 한 번 흔들렸다는 이유만으로 Luna 단계를 Terra로 올리지 않는다.
- 실패한 revision 때문에 이전 성공 결과를 삭제하거나 덮어쓰지 않는다.
- 운영 중인 Flyway migration의 checksum을 바꾸지 않는다.


새 평가 이름을 사용한다. 원본 DB의 기사·관측·원리 3개 테이블만 읽어 `economic_briefing_review_<이름>`에 복사하고 V26을 적용한다. 사용자·인증 테이블은 복사하지 않는다. 스케줄러·공개 브리핑 DB 저장은 실행하지 않는다. 실제 Java 선별·추출·설계·검색·편집 코드를 호출하며 한 편 평가에서는 제목 사전선별만 생략한다. 결과의 SUCCESS는 코드 검증 통과이며 사용자 품질 승인이 아니다.

산출물은 git 제외된 `pipeline-debug/beginner-memory/<이름>/`의 `article.json`, `corpus.sql`, `cache/`, `result.json`, `review.md`, `feedback.json`이다. `--cache-from <이전 평가 경로>`를 주면 원문·DB 복사본·요청별 API 응답을 재사용하고, 요청이 바뀐 단계만 실제 호출한다. 사용자 피드백은 이전 평가의 `feedback.json`과 비교 기록에 별도로 남긴다. 완료한 평가 DB와 원문 파일은 자동 삭제하지 않는다.

원본 DB에 없는 지정 기사는 원문을 먼저 고정한 뒤 `--article-file <ArticleEntity 행 형식 JSON>`으로 전달한다. 이 자료는 평가 DB에만 넣는다. `--cache-from`과는 함께 사용할 수 없으며, 후속 캐시 실행에서는 보존된 `article.json`을 평가 DB에 다시 반영한다.

기본 선별이 제외한 기사도 사용자가 직접 지정해 질문·기억 생성을 시험할 때는 `--selected-by-user`를 사용한다. 이 옵션은 평가 전용 진입점에서 기사 선별만 생략하고 trace에 `USER_SELECTED_FOR_REVIEW`를 남긴다. 기본 선별 결과를 먼저 보존하고 두 실행을 구분한다. 추출·설계·검색·편집과 비용·근거 검증은 그대로 적용하며 운영 선별 기준을 수정한 것으로 취급하지 않는다.

운영 로그에 API key, 관리자 token, 전체 프롬프트, 원문 전체를 남기지 않는다. OpenAI 로그는 모델명과 usage만 기록한다.

## 15. 배포 현실과 확인

현재 `.github/workflows/deploy.yml`은 이름과 주석 그대로 **DEV만** 자동 배포한다.

```text
main push
  → Windows self-hosted runner
  → backend test + bootJar
  → DEV DB economic_briefing_dev migration
  → DEV :8081 재시작
  → /api/health/briefing 확인
```

PROD `:3000`과 운영 DB는 이 workflow가 건드리지 않는다. GitHub Actions가 성공했다고 “운영 배포 완료”라고 보고하면 안 된다.

운영 배포는 Windows 운영 디렉터리의 관리자 PowerShell에서 별도로 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\deploy.ps1 -Test
```

이 스크립트는 기존 JAR과 `frontend/dist`를 백업하고, 테스트·빌드·서비스 재등록·health check를 수행하며 실패하면 이전 산출물로 롤백한다. V24는 구 테이블을 삭제하는 DB 변경이므로 운영 최초 적용 직전에는 별도 `pg_dump`도 반드시 만든다. 애플리케이션 산출물 롤백만으로 삭제된 테이블이 복구되지는 않는다.

배포 후 확인:

1. 프로세스와 `/api/health/briefing`이 정상인가
2. 이 V2를 배포한다면 Flyway가 V26까지 적용됐는가
3. `/api/briefings/latest`가 최신 SUCCESS만 반환하는가
4. 관리자 run 목록에서 usage와 trace가 보이는가
5. 웹의 “오늘의 경제흐름”에서 흐름·출처·원문 근거가 표시되는가
6. 다음 매시 05분 수집과 다음날 05:10 분석이 실제로 실행됐는가
